# Portfolio Health core methodology v1

`portfolio-health-v1` is the first deterministic Portfolio Health calculation slice. It covers position concentration, top-three concentration, valuation completeness, cost-basis completeness and asset-class allocation.

Inputs are owner-scoped persisted positions plus an explicit source cutoff and a positive price observation at or before that cutoff for each position. A later observation is rejected to prevent look-ahead. Missing prices remain missing and make valuation/concentration incomplete; they are never replaced by zero.

For a complete valuation, position value is `quantity × current price`, total value is the sum of all position values, position concentration is `position value ÷ total value × 100`, and top-three concentration is the sum of the three largest position percentages. Largest-position values above 15% or top-three values above 45% are advisory; values above 25% or 60% respectively require review.

Threshold comparisons use the unrounded concentration values. Percentages are rounded to two decimal places only for returned display fields, so a value just above a boundary cannot be hidden by presentation rounding. A value exactly on a boundary does not cross that boundary because the approved thresholds use `>` rather than `>=`.

Cost-basis completeness is the percentage of positions with a non-negative average cost and a valid three-letter cost currency. A missing cost remains null, reduces completeness and blocks any future unrealised-return claim. It does not silently become zero.

Asset-class allocation groups complete position values by the canonical lower-cased `instruments.asset_type` and returns each class as a percentage of complete portfolio value. A missing or blank canonical mapping sets `assetAllocationComplete` to false, returns no allocation percentages and records `MISSING_ASSET_TYPE:<position-id>`; it is never guessed or grouped into a fabricated class.

Optional target allocations are normalized to lower-case asset keys, require unique non-negative percentages totaling 100 within 0.01 percentage points, and participate in the deterministic source identity. No configured target returns `NOT_CONFIGURED`. With complete current allocation, absolute drift above 5 percentage points is advisory and above 10 requires review; exact boundaries do not cross because the approved thresholds are strict `>`. Incomplete current allocation returns `INCOMPLETE_DATA`, not a fabricated drift.

Drift thresholds are evaluated from unrounded current allocations; only returned percentages are rounded to two decimals. Canonically equivalent target objects produce the same source identity regardless of key case, surrounding whitespace, insertion order or numeric-string representation.

Overall snapshot completeness is the lowest of valuation coverage, cost-basis coverage and canonical asset-type mapping coverage. Therefore a portfolio with complete prices and costs but an unmapped instrument remains `INCOMPLETE_DATA`, never `HEALTHY`.

The deterministic core now calculates currency/FX exposure, watchlist overlap, issuer exposure, theme exposure and freshness from explicit validated evidence; return measures remain outside this version. The undeployed trusted runtime candidate connects canonical price/FX, owner-filtered watchlist, effective-dated issuer and Opportunity-theme evidence, writes immutable `portfolio_health_snapshots`, and supplies the authenticated Portfolio Health UI. Issuer evidence remains incomplete in hosted execution because its local contract is undeployed and unseeded; eligible-session freshness remains incomplete because its authoritative calendar contract does not exist. These are local-candidate capabilities only and do not establish hosted deployment or replay.

## Issuer-concentration data-contract diagnostic

The current hosted `instruments` relation exposes `id`, `symbol`, `instrument_name`, `asset_type`, `exchange_code`, `currency_code`, `country_code`, `is_active` and `created_at`; it has no canonical issuer identifier. The repository now contains the local, unapplied `20260903023351_my_dashboard_issuer_identity_v1.sql` candidate defining trusted canonical issuer identities and non-overlapping effective-dated instrument mappings. The undeployed trusted evaluator queries that candidate contract, but hosted production has no equivalent relation, so the query cannot run there until a separately authorised deployment and seed. `instrument_name` is a display label and must not be treated as issuer identity because multiple securities may share an issuer while funds, crypto and FX names do not represent the same legal concept.

Issuer concentration is integrated in the local runtime candidate but remains unavailable in hosted execution because the schema candidate is undeployed and unseeded. The contract provides an explicit canonical issuer entity and versioned instrument-to-issuer mapping with provenance. Equity and ETF positions without a required mapping must make issuer concentration `INCOMPLETE_DATA`; naturally non-corporate asset classes must be explicitly classified `NOT_APPLICABLE`, not silently grouped by name. Percentages use complete portfolio value as denominator, combine all mapped instruments for one issuer, and apply the approved strict >20% advisory and >30% review thresholds before display rounding.

The pure local calculation slice accepts an explicit effective mapping per position. The trusted candidate now queries the unapplied issuer contract at the UTC source-cutoff date, rejects provenance dated after that cutoff, rejects more than one effective mapping per instrument and expands the selected mapping to every owner-scoped position holding that instrument. It combines mapped position values by canonical issuer ID against complete portfolio value, returns `NOT_APPLICABLE` when every position is explicitly non-corporate, and fails closed with `MISSING_ISSUER_MAPPING:<position-id>` when any mapping is absent. The exact applicability, issuer identity, provenance and validity window participate in snapshot source hashing. Source and methodology labels must be non-empty, already trimmed and free of control characters; a non-null provenance URL must also be already trimmed and be an absolute HTTPS URL without whitespace/control characters, embedded credentials, a query string or a fragment. Null remains the explicit state when no public evidence URL exists.

Issuer thresholds use raw percentages before two-decimal presentation rounding. The mapping set must be exactly one-to-one with the evaluated portfolio positions: missing mappings produce incomplete evidence, while duplicate or out-of-portfolio mappings are rejected. The denominator is always complete portfolio value, including explicitly non-corporate positions.

## Opportunity-theme exposure data-contract diagnostic

The current contract is many-to-many: `opportunity_theme_instruments` identifies a mapping by theme, instrument and exposure type. One held instrument may therefore contribute to several themes, and a theme may contain several exposure types. Theme percentages are overlapping lenses over the same complete portfolio value; they are not allocation buckets and must never be added together as though they total 100%.

Only active mappings to active or watch themes are eligible for a current calculation. Inactive mappings remain historical/current-state evidence but contribute no exposure. `exposure_score` records mapping strength on a 0–100 scale; the existing schema and product contract do not define it as a portfolio-value weight, so the first calculation must not multiply holding value by that score. `exposure_type` and `rationale` are explanatory evidence and do not imply a Buy/Sell recommendation.

Absence of a mapping cannot safely prove zero thematic exposure because the present model has no per-instrument coverage/applicability record. A held instrument with no explicit mapping evidence must therefore produce `INCOMPLETE_DATA`, not zero exposure. An empty portfolio can be `NOT_APPLICABLE`; a configured portfolio cannot be declared `NOT_APPLICABLE` merely because mappings are absent. A future explicit coverage contract is required to distinguish reviewed-and-unmapped instruments from instruments that have not been assessed.

The hosted read-only diagnostic found 10 themes and 25 mapping rows: 24 active, one inactive, no null scores, no duplicate theme/instrument pair expressed through multiple exposure types, and the current exposure types `beneficiary`, `direct`, `enabler`, `infrastructure` and `supplier`. The schema also permits `substitute` and `risk`, so calculation and presentation must tolerate those valid values even though no current row uses them.

The mapping table is mutable current-state data with timestamps but no effective-dating or immutable revision identity. Reproducible snapshots must therefore hash the exact eligible mapping rows and theme states selected at the source cutoff; `updated_at` alone is not a historical lookup mechanism. This diagnostic did not implement a calculation, persist a snapshot, change hosted Supabase, or connect UI.

The pure local calculation now accepts explicit mapping rows containing position, theme, exposure type, score, mapping-active state and theme state. Every held position requires at least one mapping evidence row; missing evidence returns `INCOMPLETE_DATA`. Active mappings to `active`/`watch` themes contribute the position's full value against complete portfolio value, while inactive mappings or `paused`/`archived` themes contribute nothing but still establish explicit coverage. Multiple exposure-type rows for the same position/theme are counted once, and one position may contribute fully to multiple themes. Scores remain validated evidence and never weight value. This calculation is not connected to runtime queries or persistence.

## Currency/FX exposure data-contract diagnostic

The initial core multiplied quantities by instrument-currency prices and summed those values directly, which was valid only when every valued instrument currency equalled the portfolio base currency. The current core instead requires explicit timestamp-bounded FX conversion for every non-base position; absent or invalid conversion keeps mixed-currency totals, concentration, allocation, issuer exposure and theme exposure `INCOMPLETE_DATA`. Nominal amounts in USD, CAD, CNY and JPY are never added as if they were the same unit.

Currency exposure is calculated in portfolio base currency. For instrument currency `X` and portfolio base `B`, a canonical `X/B` forex observation supplies base-currency units per instrument-currency unit directly; a canonical `B/X` observation supplies the inverse. `X = B` uses rate 1 without an FX row. V1 does not triangulate through a third currency. Missing direct/inverse evidence, a non-positive rate, a future observation, or an observation outside the approved freshness window blocks the base-currency total and all percentage measures rather than becoming zero or rate 1.

The hosted read-only diagnostic found 80 instruments across CAD, CNY, JPY and USD. Five active `forex` instruments exist (`EUR/USD`, `AUD/USD`, `USD/CAD`, `USD/JPY`, `GBP/USD`) with both `1day` and `quote` observations and populated close/adjusted-close values in the inspected result set. There is no CNY pair. With an AUD base, USD has a direct/inverse path through `AUD/USD`, but CAD, CNY and JPY have no direct AUD pair and cannot be converted under the approved no-triangulation rule. Their presence must therefore be surfaced as incomplete evidence when held.

The `market_observations.currency_code` field is the observation's quote/reporting currency; it is not by itself an FX conversion contract. Pair direction comes from the canonical forex instrument symbol and must be validated rather than inferred from the observation currency. Reproducible output binds the exact price and FX observation IDs, timestamps, direction and rates into the source identity. The original diagnostic made no calculation, schema, hosted-data, snapshot, runtime or UI change; the later local slices described below implemented the pure calculation, canonical identity and undeployed runtime integration.

Runtime integration must first resolve exactly one active `data_providers` row whose `provider_code = 'tiingo'`; zero or multiple active rows fail closed and no provider UUID ordering or fallback is allowed. Held instruments must load canonical `currency_code`, while both price and FX observations must use that provider, `interval_code = '1day'`, `observed_at <= source_cutoff` and stable `observed_at DESC, id DESC` ordering. FX pair discovery considers only active canonical `forex` instruments whose normalized symbol is exactly `X/B` or `B/X`. No pair is incomplete evidence; simultaneous direct and inverse canonical instruments are ambiguous and must fail closed rather than silently prefer one. Portfolio-health FX must align to the selected position-price session; until an authoritative eligible-session/calendar rule is integrated, missing exact aligned FX remains `INCOMPLETE_DATA` and freshness remains explicitly unresolved. The next implementation slice should correct provider/interval-constrained price selection and instrument currency before adding FX conversion.

The canonical price-read slice now implements that prerequisite locally: exactly one active Tiingo provider is required; held instruments load `currency_code`; daily observations are URL-bounded by held instrument IDs, constrained to Tiingo `1day` and the source cutoff, and fully paged in stable timestamp/row-ID order. Provider ID, interval and observation currency join the exact row ID and timestamp in the immutable source payload. Equal-time observation selection is deterministic independent of input order.

The local canonical FX-read slice discovers only active `forex` instruments with exact normalized `AAA/BBB` symbols involving the portfolio base currency and a held currency. A held currency with both direct and inverse canonical instruments fails closed as ambiguous. FX observations use the same Tiingo provider and `1day` interval as prices, are URL-bounded and completely paged, and qualify only when their parsed instant exactly equals the selected position-price instant. Missing pairs, missing exact-session observations and invalid rates remain explicit `MISSING_FX` incomplete states. Each mapping binds the position, pair instrument, normalized direction, provider, interval, observation ID/time and positive rate into immutable source identity; no triangulation, previous-session substitution or fallback source is permitted.

The pure local calculation now optionally accepts a portfolio base currency, explicit instrument currency per position and at most one direct/inverse FX observation per non-base position. It converts every complete position value before calculating total, concentration, asset allocation, issuer exposure or theme exposure. Missing currency or FX evidence makes valuation and currency exposure `INCOMPLETE_DATA`; same-currency positions use rate 1 and may not supply an FX row. Non-base exposure above 35% is advisory and above 50% requires review, using unrounded percentages before two-decimal presentation rounding. Runtime lookup and source-hash integration are present in the undeployed trusted candidate; authoritative eligible-session freshness evaluation remains unavailable.

## Watchlist/portfolio overlap data-contract diagnostic

Watchlist overlap is an informational identity comparison, not a financial allocation or health threshold. The canonical key is `instrument_id`: each unique instrument held in the selected portfolio is compared with the union of instruments in every watchlist owned by the same permanent user. Position quantity, cost, list name, default-list status and the number of lists containing an instrument do not increase its overlap weight.

The result should expose unique held-instrument count, unique watched-instrument count, overlapping instrument IDs/count and `overlap count ÷ unique held-instrument count × 100`. Duplicate watchlist membership and multiple portfolio rows for one instrument must be deduplicated defensively. An empty portfolio is `NOT_APPLICABLE`; an explicitly loaded empty watchlist union is a complete zero-overlap result, not missing data. A null/failed watchlist input remains `INCOMPLETE_DATA`, not an assumed empty set.

Both sources are private and must share the validated permanent owner. `portfolio_positions.owner_user_id` is explicit; `watchlist_items` ownership is inherited through `watchlists`, whose current RLS policies require a non-anonymous authenticated owner. Any trusted runtime read must filter the portfolio and watchlists by the validated owner in addition to relying on RLS/service boundaries. Exact portfolio-position and watchlist-item identities must participate in a persisted source hash because either side can change after evaluation.

No hosted personal rows were queried for this diagnostic: schema, policies and existing owner-filtered application reads are sufficient to define the pure contract without accessing private user content. No calculation, schema, data, snapshot, runtime or UI change was made.

The pure local calculation now optionally accepts the loaded watched-instrument set. Omission remains `NOT_CONFIGURED`, explicit null is `INCOMPLETE_DATA`, an empty loaded set is a complete 0% result, and an empty portfolio is `NOT_APPLICABLE`. It reports deduplicated held/watched counts, sorted overlapping IDs and overlap percentage over unique held instruments. Missing held-instrument identity fails closed. Runtime private reads and source-hash integration remain later slices.

## Price/FX freshness data-contract diagnostic

Freshness is measured in eligible market sessions, not elapsed hours or calendar days. Weekends, exchange holidays and periods before an instrument's next eligible session must not make evidence stale. For each held instrument, the trusted loader must resolve the latest canonical `1day` price observation at or before the source cutoff and compare its session key with the instrument's expected trading calendar. Required FX evidence uses the same selected price session; under V1 its canonical FX observation must have exactly the same `observed_at`.

The pure calculation must receive explicit session-age evidence resolved upstream: zero missed eligible sessions is current, one missed session is `ADVISORY`, and two or more is `NEEDS_REVIEW`. Thresholds are counts, so the approved wording "after one" and "after two" is inclusive at 1 and 2. A missing price/FX observation, unknown calendar, ambiguous canonical provider, future observation, or inability to resolve expected sessions is `INCOMPLETE_DATA`, never a stale count guessed from wall-clock subtraction.

Portfolio freshness is the worst state across every required price and FX input, while retaining per-position reasons and ages. Same-currency positions require no FX freshness row. A non-base position cannot be freshness-complete unless both price and exact-session FX evidence are complete. Exact price/FX observation IDs, timestamps, provider identity, interval, calendar/methodology version and source cutoff must participate in source identity.

The pure local calculation now optionally accepts one resolved freshness mapping per position. Each mapping supplies a non-negative integer price-session age; a non-base position also requires a non-negative integer FX-session age, while a same-currency position must not supply one. Portfolio state is the worst required input: zero missed sessions is `CURRENT`, one is `ADVISORY`, and two or more is `NEEDS_REVIEW`. Omitted evidence remains `NOT_CONFIGURED`, explicit null or a missing position mapping is `INCOMPLETE_DATA`, and an empty portfolio is `NOT_APPLICABLE`. Returned per-position ages are deterministically ordered.

The trusted runtime candidate constrains price and FX observations to canonical provider and `interval_code = '1day'`, but still has no authoritative trading calendar and therefore cannot resolve eligible-session age. Freshness remains explicit incomplete evidence in runtime, while the pure aggregation and canonical source payload support deterministic externally resolved ages. It never derives age from timestamps or calendar-day subtraction.

## Canonical source identity support

The runtime-neutral request helper can now canonically serialize explicit currency/FX, issuer, theme, watchlist and freshness evidence for immutable source hashing. It normalizes the same currency, exposure-type, lifecycle and numeric values consumed by the core; orders identity-bearing rows deterministically; rejects duplicate evidence identities; deduplicates set-like watched instrument IDs; and preserves omitted, explicit null and loaded-empty states as different payloads. Watchlist rows use the hosted `(watchlist_id, instrument_id)` composite key and never invent a standalone item ID. Any change to an FX rate, issuer identity, theme evidence, watchlist membership or resolved freshness age therefore changes the source hash.

The canonical payload contract is used by the undeployed trusted function for the evidence families it currently loads: currency/FX, watchlist membership, issuer mappings and Opportunity-theme mappings. Required issuer IDs must use the lowercase canonical UUID representation before hashing, matching database UUID output and preventing malformed, case-only or whitespace-only immutable identity variants. Issuer mappings are unavailable in hosted execution until the local schema is separately approved, deployed and seeded; resolved freshness ages still lack a hosted calendar contract. Both therefore remain explicit incomplete evidence rather than fabricated values in current hosted snapshots.

Cutoff-effective issuer mappings are loaded in bounded held-instrument batches and fully paged with stable instrument, validity-start and methodology ordering. The evaluator therefore cannot treat a Data API row limit as complete evidence; every returned eligible row reaches the duplicate-per-instrument ambiguity check and canonical source payload.

## Runtime integration readiness

Current hosted schema maps target allocations and base currency to the validated owner-scoped `portfolios` row; positions to `portfolio_positions` with both portfolio and owner predicates; asset and instrument currency to canonical `instruments`; price evidence to canonical `market_observations` constrained to `interval_code = '1day'`, one approved provider and the source cutoff; theme evidence to `opportunity_theme_instruments` joined to `opportunity_themes`; and watchlist evidence to owner-filtered `watchlists` joined to `watchlist_items`.

Two hosted gaps prevent a complete runtime integration. The local issuer-identity migration is not present in hosted migration history, so `canonical_issuers` and `instrument_issuer_mappings` do not exist in the connected project. Freshness can bind observation/provider/interval data, but the hosted model has no authoritative exchange-to-trading-calendar/session relation from which eligible missed sessions can be resolved. Both gaps must remain explicit incomplete evidence until separately approved schema/methodology work exists.

`watchlist_items` uses `(watchlist_id, instrument_id)` as its primary key and has no standalone item ID. Its source identity must therefore use that hosted composite identity, not invent a row ID. Service-role reads in the trusted function must continue to constrain every private relation to the already validated permanent owner because privileged access bypasses RLS; browser grants and policies remain unchanged.

The first trusted runtime integration now loads all owner-filtered `watchlists`, batches the owner-derived list IDs to keep Data API URLs bounded, pages every `watchlist_items` row constrained to each exact batch, derives the deduplicated watched-instrument union, and passes both composite membership rows and the union to the deterministic core and source hash. An explicitly loaded owner with no watchlists therefore produces a complete zero-overlap result rather than `NOT_CONFIGURED`. This local candidate remains undeployed.

The trusted runtime candidate batches held instrument IDs, pages exact `opportunity_theme_instruments` mapping identity and activity rows, then resolves every referenced `opportunity_themes.status`. Each mapping is expanded to the exact owner position that holds its instrument before entering the core and source hash. Missing mappings remain incomplete evidence rather than zero exposure. The database permits a null `exposure_score`; Portfolio Health preserves that null because theme allocation is based on mapped position value and is deliberately not weighted by an Opportunity score. This local candidate remains undeployed.
