### Definition of Done

Definition of Done: **Ownership and access rules are defined before enabling writes.**

| Check | Verdict | Independent evidence |
|---|---|---|
| Canonical end-user identity authority is defined | VERIFIED | `documentation/security/watchlist-auth-model.md` names Supabase Auth as the canonical identity provider and `auth.users.id` as the ownership key. Live Supabase confirms `watchlists.owner_user_id` and `alerts.owner_user_id` both reference `auth.users(id)` with `ON DELETE CASCADE`, so the decision aligns with the existing schema rather than inventing a parallel identity model. |
| Watchlist ownership semantics are explicit | VERIFIED | The contract requires exactly one permanent authenticated owner per watchlist, makes `owner_user_id` mandatory before writes are enabled, prevents normal client ownership transfer, and makes item ownership inherit through `watchlist_id`. Live schema confirms the existing watchlist-item parent FK and `(watchlist_id, instrument_id)` primary key support that model. |
| Read/write access rules are explicit for each actor | VERIFIED | The access matrix explicitly denies unauthenticated users, authenticated anonymous users and other users; permits permanent authenticated users to access only their own watchlists/items; and reserves trusted service access for backend/migration use. There is no public/shared/team watchlist model in v1. |
| Required pre-write database hardening is defined | VERIFIED | The contract requires removal or deliberate migration of the ownerless fixture, `owner_user_id NOT NULL`, owner index, one-default-per-owner enforcement, `updated_at` maintenance where needed, minimal grants, and owner-scoped RLS for both parent and item tables before any write UI is enabled. |
| Future RLS ownership boundary is defined | VERIFIED | The contract specifies `TO authenticated` policies using `(select auth.uid())`, permanent-user/anonymous-auth rejection, owner-only SELECT/INSERT/UPDATE/DELETE on `watchlists`, and parent-owner `EXISTS` checks for `watchlist_items`. It also explicitly prohibits browser service-role use. |
| Current live database baseline matches the documented decision context | VERIFIED | Live Supabase shows zero `auth.users`, one watchlist, one item, one ownerless watchlist and one default watchlist. `watchlists.owner_user_id` is currently nullable. Both watchlist tables have RLS enabled and zero policies. Broad legacy grants remain for `anon`, `authenticated` and `service_role`, exactly as documented. No watchlist update trigger exists. |
| Writes/read access have not been enabled prematurely | VERIFIED | With RLS enabled and zero policies, independent role probes under `anon` and unauthenticated `authenticated` each returned zero visible watchlists. Repository search found no watchlist application implementation, and `lib/supabase.ts` still uses the public publishable key with `persistSession: false` and `autoRefreshToken: false`. MON-001 therefore defines the model without activating the write path. |
| Monitoring identity decision is compatible with later alert work | VERIFIED | Live `alerts.owner_user_id` already references `auth.users(id)` and `alerts.watchlist_id` references `watchlists(id)`. Reusing the same ownership key is structurally compatible with MON-003/MON-004. |
| Canonical documentation surfaces the decision | VERIFIED | `documentation/README.md` links `documentation/security/watchlist-auth-model.md`, and `documentation/supabase-data-model.md` records the live MON-001 baseline, the selected ownership model and the MON-002 activation gate. |
